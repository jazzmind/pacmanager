# Living assurance and graduation

Architecture, operational readiness and inventory are data owned by the artifact. Reports are generated views of that data, not separately maintained Word files. `demo/assurance.js` defines a strict schema, generators, validation rules and report renderers. `assurance.json` is the portable source included in graduation and code publication.

## How changes propagate

1. A new app immediately has a structured record with explicit unknowns.
2. The author modifies the app through `update_application`. Draft changes do not relabel the documentation for the published release.
3. The app builds and publishes. The new definition, source digest, build mode and changed-field history drive fresh architecture, readiness and BOM facts automatically.
4. Uploads, discussion counts and mock capability bindings refresh live inventory facts. These are live workspace facts, not an immutable document snapshot.
5. Authored decisions survive. A release mismatch marks them stale for re-review. Unknown recovery objectives, cost estimates or signoffs are never inferred from a successful build.
6. The next report request, preview or download uses the updated record. An open graduation preview refreshes when its release or record changes. An open JSON editor is preserved and stale saves are rejected.

The app's release history stores changed field names and source digests (latest 50 releases). Authored record history stores actor, revision and content digest (latest 50 updates). Exports preserve the current complete record; this is not a historical document archive.

## Data ownership

| Layer | Source | Change behavior |
|---|---|---|
| Observed facts | Published definition, build result, capability state, document/note counts | Regenerated by the controller |
| Managed sections | Purpose, scope, target state, app structure, generated artifacts, runtime inventory and interfaces | Refreshed automatically; author edits to managed fields are ignored |
| Owner decisions | Recovery objectives, finance owner, cost estimates, security reviews, support and risks | Preserved with evidence references; stale after release changes |
| Component inventory | Generated runtime/platform components plus authored inventory | `pac-` IDs are reserved for generated components |
| Rendered documents | One record and one template version | HTML/Markdown generated on request; no stored document copies required |

Each authored section has `status`, `text`, `owner` and `evidence`. Status is `unknown`, `proposed`, `documented` or `not-applicable`. Documented entries require an owner and evidence reference. Not-applicable entries require a rationale. Evidence references are author assertions; the platform does not verify the linked evidence or certify readiness. Independent review status always remains pending in this demo.

## Coverage of the supplied examples

The supplied examples were inspected to identify structure only. Their files, populated business details, names, endpoints and internal references are not included in this repository.

| Reference | Structured coverage |
|---|---|
| Architecture review | Purpose/scope/current/target state; stakeholders including finance; objectives/goals/constraints; classification; logical/data/development/deployment views; artifacts/APIs/stack; deviations; security/threat model/vendor MFA; DR; infrastructure/authoring/runtime AI costs; risks/NFRs/decisions/meeting notes/open items |
| Systems readiness | System/schedule/users/browsers/uptime/peak usage; vendor/legal/test environments; ARB/data review; hardware/network/server/database; monitoring/service management/logging/purge; risk/IAM/privacy/vulnerability evidence; DR/batch/performance/QA; support/controls/dependencies |
| Bill of materials | Shared dependencies and ownership; cloud resources; DevOps/repositories; third-party software; endpoints; secret references; encryption/certificates; storage; observability; runtime permissions; vulnerability remediation; standards references; typed component inventory |

The operational BOM is not a complete scanned SBOM. Exact deployed versions, image digests, package licenses and transitive OS dependencies require external inventory evidence. HTML includes an observed demo topology; target and disaster-recovery diagrams remain evidence-backed owner work. Exports are HTML, Markdown and JSON, not replicas of the reference DOCX formatting. HTML is print-friendly for browser PDF printing.

## MCP guidance and tools

The demo exposes reusable guidance through standard MCP **prompts and resources**, alongside executable tools. It does not depend on a client-specific skill installer.

- Prompts: `prepare_graduation(artifactId)` and `evolve_application(artifactId, change)`.
- Resources: `pac://assurance/schema` and `pac://assurance/guide`.
- Tools: `get_assurance`, `get_assurance_schema`, `update_assurance`, `preview_assurance_document`.
- Existing tools perform app inspection, definition changes, builds and publication.

`get_assurance` returns `{record, completeness}`. To save owner decisions, pass `id`, `revision: record.recordRevision`, `release: record.release` and the full edited `data` object to `update_assurance`. The controller validates it and checks concurrency. Consult `managedFields` before editing; those fields always regenerate from app state. Keep secrets and raw knowledge content out of assurance prose.

Suggested demo prompt after v1:

> Change this into a knowledge workspace called Team knowledge desk, use a plum accent, and describe it as the team's onboarding guidance hub. Build and publish the change. Then preview the architecture review, systems readiness and bill of materials and show what changed for the new release. Flag anything that needs owner re-review.

This makes a supported template/style/definition change. Arbitrary custom behaviors remain outside the constrained runtime. The assistant must not imply that editing a brief implements unsupported functionality.

## GitHub publication

GitHub is disabled by default. For the local demo, configure `PAC_GITHUB_TOKEN` in the server environment and `PAC_GITHUB_REPOSITORIES` as an exact comma-separated `owner/repository` allowlist. Use a narrowly scoped GitHub App token or fine-grained token with Contents write access to the intended existing **private** repositories. Initialize each target repository with a README first. No token belongs in client configuration, prompts, checked-in files or exports.

In **Graduate**, choose the destination, click **Prepare publication**, inspect the exact file contents, check the confirmation and click **Publish reviewed code**. The plan is bound to an app/record fingerprint, destination, file digest and five-minute expiry. The publisher creates a new `pac/<artifact>/v<release>-<unique>` branch with an independent source tree. It does not update the default branch or open/merge a PR. A maintainer can later adopt the branch or copy the source into the desired repository structure.

The publish file set includes source, an empty data snapshot, structured assurance, report views, Docker/Score starters and checksums. Uploaded document content, team notes, claims rows, sessions and credentials are excluded. The brief and owner-authored assurance prose are included and must be reviewed for sensitive information. The full downloaded archive still contains workspace data.

Browser owner sessions can prepare and approve publication. MCP bearer credentials cannot execute this publication endpoint. The server fixes the API host to `api.github.com`, rejects redirects, checks private visibility and allows only configured destinations. Failed/expired/changed plans need a fresh review. Network failures can leave unreferenced Git objects; an ambiguous final reference response should be checked in GitHub before retrying. This is not a complete GitHub App installation/OAuth workflow.

For Kubernetes, the default-deny deployment intentionally cannot reach GitHub. Leave publishing disabled until an administrator supplies a narrowly scoped egress route and secret injection for this controller capability. This change does not open blanket internet access or modify the existing cluster manifests. Local publication performs no network calls until the owner confirms.

## Verification

`test/assurance.test.js` verifies automatic v1-to-v2 document updates, retained/stale owner decisions, managed inventory, report escaping, schema/evidence rules, cross-artifact access, MCP prompt/resource/tool behavior and reviewed GitHub publication using an injected GitHub API double. It also verifies actual MCP update/build/publish calls and document refresh for the new release. GitHub destination permissions, a real artifact publication and desktop/browser rehearsal still require deployment verification. No uploaded reference content was sent to GitHub.
